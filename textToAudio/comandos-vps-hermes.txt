==========================================================
  GUÍA DE COMANDOS — VPS + HERMES AGENT
  (operar desde la terminal de tu Mac)
==========================================================

Notas previas:
- Tu Mac y el VPS son máquinas distintas. Desde el Mac "entras"
  al VPS por SSH. Una vez dentro, todos los comandos corren en
  el VPS, no en el Mac.
- Hermes vive en la carpeta ~/hermes del VPS.
- VitaMap vive en su propio docker-compose (NO lo toques al operar
  Hermes; son contenedores separados).
- Sustituye IP_DEL_VPS por la IP real de tu servidor.


----------------------------------------------------------
1) CONECTARSE AL VPS
----------------------------------------------------------

# Entrar por SSH (desde tu Mac):
ssh root@IP_DEL_VPS

# Salir del VPS (volver a tu Mac):
exit


----------------------------------------------------------
2) IR A LA CARPETA DE HERMES
----------------------------------------------------------

cd ~/hermes

# Ver qué archivos hay:
ls -la


----------------------------------------------------------
3) OPERAR HERMES (encender / apagar / reiniciar / estado)
----------------------------------------------------------
# (Ejecutar siempre desde dentro de ~/hermes)

# Encender Hermes (en segundo plano):
docker compose up -d

# Apagar Hermes (no borra nada, los datos se conservan):
docker compose down

# Reiniciar (p. ej. tras cambiar configuración):
docker compose restart

# Ver si está encendido y su estado:
docker compose ps

# Ver el consumo de RAM/CPU en vivo (Ctrl+C para salir):
docker stats hermes


----------------------------------------------------------
4) VER LOS LOGS (lo que está haciendo el agente)
----------------------------------------------------------

# Seguir los logs en vivo (Ctrl+C deja de mirar; NO apaga Hermes):
docker compose logs -f

# Ver solo las últimas 50 líneas:
docker compose logs --tail 50

8) ACTUALIZAR HERMES A LA ÚLTIMA VERSIÓN
----------------------------------------------------------
# IMPORTANTE: como usas una imagen propia (Dockerfile con
# yt-dlp + ffmpeg), NO actualices con "pull" a secas, porque
# perderías yt-dlp. Hay que RECONSTRUIR con --build para que
# tu imagen se rehaga sobre la última versión de Hermes y
# vuelva a incluir yt-dlp y ffmpeg.

cd ~/hermes

# 1. Baja la última versión base de Hermes:
docker pull nousresearch/hermes-agent:latest

# 2. Reconstruye TU imagen sobre esa base y levanta:
docker compose up -d --build

# 3. Limpia la caché de build que deja la reconstrucción:
docker builder prune -af

# 4. Comprueba que yt-dlp y ffmpeg siguen ahí:
docker compose exec hermes yt-dlp --version
docker compose exec hermes ffmpeg -version

# (Reconstruir también actualiza yt-dlp a su última versión,
#  útil porque YouTube cambia y yt-dlp se queda obsoleto.)

11) CONEXIÓN A GITHUB (claves SSH / deploy keys)
----------------------------------------------------------
# Modelo de dos "identidades", una clave por cada una:
#   - Clave 1 (vitamap_readonly): SOLO LECTURA del repo privado
#       Marcomano28/VitaMap  (deploy key sin "Allow write access").
#   - Clave 2 (vitawende_write): ESCRITURA en el repo de la cuenta
#       máquina andereHermes/VitaWende (deploy key CON write access).
#
# Las claves viven en ~/hermes/data/ssh/ (en el VPS), que se monta
# dentro del contenedor como /opt/data/ssh/. Son del usuario hermes
# (uid 10000) y PERSISTEN entre reinicios y reconstrucciones --build.
# No hay que rehacer nada salvo que borres esa carpeta.
#
# IMPORTANTE: una "deploy key" va atada a UN repo. Por eso hay una
# clave por repo, y cada comando elige la suya con GIT_SSH_COMMAND.

# Comprobar que la clave de lectura autentica (debe decir "Hi
# Marcomano28/VitaMap! ... successfully authenticated"):
ssh -i ~/hermes/data/ssh/vitamap_readonly -o StrictHostKeyChecking=accept-new -T git@github.com

# El clon de VitaMap está dentro del contenedor en:
#   /opt/data/repos/VitaMap   (en el VPS: ~/hermes/data/repos/VitaMap)

# ACTUALIZAR EL ESPEJO (traer cambios de VitaMap y subirlos a VitaWende):
docker compose exec hermes sh -c '
cd /opt/data/repos/VitaMap
GIT_SSH_COMMAND="ssh -i /opt/data/ssh/vitamap_readonly -o IdentitiesOnly=yes" git pull origin main
GIT_SSH_COMMAND="ssh -i /opt/data/ssh/vitawende_write -o IdentitiesOnly=yes" git push mirror main
'

# Si algún día RECREAS una clave, recuerda devolverle el dueño a
# Hermes para que pueda leerla (si no, dará "Permission denied"):
#   chown 10000:10000 ~/hermes/data/ssh/NOMBRE_DE_LA_CLAVE
#   chmod 600 ~/hermes/data/ssh/NOMBRE_DE_LA_CLAVE

# Nota: el GITHUB_TOKEN del ~/hermes/data/.env NO se usa en este
# flujo (vamos por SSH). Puede quedarse ahí; es inofensivo.

16) QUE HACE LA SKILL ACTUAL
----------------------------------------------------------
# La skill actual no es un prompt largo de investigacion libre. Es un
# procedimiento operativo.
#
# Entrada:
#   Solo un tema, por ejemplo:
#     Tema: Agni en sentido amplio
#     Tema: Ama
#     Tema: Ojas
#     Tema: Ashwagandha
#
# Salida:
#   Un paquete de .md revisables para VitaMap.
#
# Logica editorial:
#   - Primero audita que tarjetas tienen sentido para el tema.
#   - No genera tarjetas por cuota.
#   - Cada tarjeta necesita fuente suficiente e intencion recuperable distinta.
#   - T1 solo si hay pasaje clasico verificable.
#   - Si T1 no pasa la puerta, crea T1-BLOCKED.md.
#   - T2 cubre contexto academico/tradicional.
#   - T3 solo si hay una pregunta moderna evaluable.
#   - Para plantas/preparados puede considerar M1/M2/M3/M4.
#   - No convierte Ayurveda en biomarcadores ni diagnosticos modernos.
#
# Para conceptos como Agni, la matriz posible es:
#   - T1: pasaje clasico verificable.
#   - T2: Agni general, Paka, tipologia.
#   - T2 separada: Jatharagni/estados, si la fuente lo justifica.
#   - T2 separada: Bhutagni/Dhatvagni, si aporta una intencion distinta.
#   - T3: medicion/operacionalizacion moderna, solo si hay fuente adecuada.


----------------------------------------------------------
17) VALIDACIONES QUE DEBE HACER LA SKILL
----------------------------------------------------------
# Antes de crear MANIFEST.md, la skill debe leer de vuelta las tarjetas y
# comprobar:
#
#   - La primera linea del archivo es exactamente ---.
#   - El frontmatter se cierra con otra linea --- antes del cuerpo.
#   - tarjeta_id coincide con el nombre del archivo sin .md.
#   - El nombre del archivo esta en minusculas y kebab-case.
#   - source_url es URL cruda, no Markdown.
#   - No hay null, none, doi: null, pmid: null, pmcid: null ni muestra: none.
#   - source_type y seccion son coherentes con corpus-taxonomy.json.
#   - No hay equivalencias falsas entre Ayurveda y biomedicina.
#   - MANIFEST.md marca duplicados viejos como ignorados, no como validos.
#
# Para PMC3221079 / "Physiological aspects of Agni", si se usa esa fuente:
#   doi: 10.4103/0974-8520.77159
#   pmcid: PMC3221079
#   publication_date: '2010'
#   source_language: en

21) CREAR MAS SKILLS EN EL FUTURO

# Reglas aprendidas:
#
# 1. Primero crear una skill unica y operativa.
#    Evitar bundles hasta que el flujo funcione de punta a punta.
